Many .NET applications encounter performance bottlenecks in database-intensive code paths. When Entity Framework Core (EF Core) repeatedly translates and compiles the same LINQ queries, it introduces overhead that can significantly impact the responsiveness of high-throughput systems. Identifying these "hot paths" and optimizing them is a common challenge for developers striving for scalable and performant applications. Pre-compiling these frequently executed queries offers a powerful solution to bypass this translation overhead.

Claude Code can accelerate this optimization process by automatically generating pre-compiled versions of your EF Core LINQ queries. Once compiled and executed for the first time, EF Core caches these queries, effectively eliminating the repeated translation and compilation work. This dramatically improves performance for queries executed thousands or even millions of times. The `claude` CLI tool facilitates this by analyzing your `DbContext` definition and a target LINQ query to produce C# code that utilizes EF Core's `CompileAsyncQuery` or its synchronous equivalent.

To leverage this, ensure your `DbContext` is defined within your project. Then, identify the specific LINQ query you wish to optimize. The `claude` CLI command targets your project and query, for instance:

```csharp
// Assume this is within YourApp.Data.MyDbContext
public async Task<List<UserDto>> GetActiveUsersAsync()
{
    // This is the LINQ query that would be identified for compilation
    var activeUsersQuery = context.Users.Where(u => u.IsActive).Select(u => new { u.Id, u.Name });
    // ... compiled query execution would go here ...
}
```

```bash
claude compile ef-query \
  --project ./YourApp.csproj \
  --context-type YourApp.Data.MyDbContext \
  --query "context.Users.Where(u => u.IsActive).Select(u => new { u.Id, u.Name })" \
  --output-file ./CompiledQueries/UserQueries.cs
```

This command directs Claude Code to locate `MyDbContext` in `YourApp.csproj`, analyze the provided LINQ query, and generate a C# file at `./CompiledQueries/UserQueries.cs` containing the compiled query implementation. The generated code will likely look similar to this:

```csharp
// Generated by Claude Code
using Microsoft.EntityFrameworkCore;
using System.Linq;
using YourApp.Data; // Assuming YourApp.Data contains User and UserDto

public static class UserQueries
{
    private static readonly Func<MyDbContext, IQueryable<UserDto>> _getActiveUsersCompiled;

    static UserQueries()
    {
        _getActiveUsersCompiled = EF.CompileQuery((MyDbContext context) =>
            context.Users.Where(u => u.IsActive).Select(u => new UserDto { Id = u.Id, Name = u.Name }));
    }

    public static async Task<List<UserDto>> GetActiveUsersAsync(MyDbContext context)
    {
        return await _getActiveUsersCompiled(context).ToListAsync();
    }
}
```

A critical limitation to understand is that compiled queries are tightly coupled to the specific `DbContext` type and the exact structure of the LINQ query. Even a minor alteration in the query's syntax or using a different `DbContext` instance (even if it's the same type) will lead to a cache miss, defeating the purpose of compilation. Therefore, rigorous testing and adherence to the original query definition are paramount. Developers must also be mindful of choosing between `CompileAsyncQuery` for asynchronous operations and its synchronous counterpart to match their application's needs.

**Try it:** Experiment by running the `claude compile ef-query` command against a common LINQ query in your EF Core project and examine the resulting C# code to see how it optimizes your database interactions.
